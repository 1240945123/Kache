# Experiment Diff And D009/D010 Optimization Design

## Context

The current layered preference strategy is functional and passes the local smoke run, but the latest experiment still leaves a large penalty surface:

- Total net income: `155022.58`
- Total preference penalty: `99510.0`
- Failed drivers: `0`
- Token usage: `0`
- Completed steps: `1843`

The largest visible bottleneck is concentrated in D009 and D010:

- D009: penalty `36100.0`, net `-3660.33`
- D010: penalty `16910.0`, net `13369.83`
- Combined penalty: `53010.0`, more than half of the total penalty

The next work should make every experiment easier to compare before changing planner behavior again. This avoids tuning blindly and gives each future model, parser, planner, or scorer change a clear before/after record.

`qwen3.5-flash` is available and must remain the only model used when a model call is required. It should stay out of the high-frequency decision path and remain a fallback for unknown strong preference parsing.

## Goals

1. Add experiment diff reporting so each new run can be compared with a previous run.
2. Add D009/D010 action timeline diagnostics to identify concrete penalty causes.
3. Use the diagnostics to guide the next planner/scorer optimization without hardcoding driver IDs or hidden dataset facts into decision logic.
4. Preserve existing summary reporting and tests.

## Non-Goals

1. Do not make the LLM choose cargo or actions in the main loop.
2. Do not hardcode D009 or D010 special behavior in production decision logic.
3. Do not read raw cargo datasets from agent decision code.
4. Do not optimize all drivers at once before the D009/D010 penalty surface is understood.

## Approach

The work has two layers.

### Layer 1: Experiment Diff Reporting

Extend the existing report generation flow around `demo/agent/evaluate_results.py`.

The report tool should support an optional baseline report input. When provided, it should produce a `Delta` section comparing the current run against the baseline.

The comparison should include:

- Total net income delta
- Total preference penalty delta
- Failed driver count delta
- Token usage delta
- Completed steps delta
- Runtime delta when both reports contain runtime
- Per-driver gross, cost, penalty, net, and action count deltas

The output should make regressions easy to spot:

- Drivers sorted by penalty increase, then net income decrease
- Positive and negative deltas shown with explicit signs
- Missing drivers treated as report data problems and called out clearly

The baseline source can be a previous markdown report generated by the same tool. If markdown parsing becomes brittle, the implementation may also add a structured JSON sidecar report and prefer that for diffing.

### Layer 2: D009/D010 Diagnostics

Add an optional diagnostic mode for selected drivers, initially used for D009 and D010. This mode should summarize action logs into a compact timeline.

The timeline should include:

- Simulation minute and day/hour representation
- Action type
- Cargo ID for accepted/taken orders when available
- Reposition target when available
- Wait duration when available
- Result acceptance flag when available
- Pickup deadhead distance and haul distance when available
- Location snapshots when available

The diagnostic output should not assume that D009 and D010 are always the targets. It should accept a list of driver IDs so the same tool can be used later for any driver with a regression.

The diagnostic report should be written under `docs/superpowers/experiments/` next to the experiment summary.

## Data Flow

1. Run the local simulation.
2. Run `calc_monthly_income.py`.
3. Run `evaluate_results.py`.
4. `evaluate_results.py` reads:
   - `monthly_income_*.json`
   - `run_summary_*.json`
   - `actions_*.jsonl`
   - optional baseline report or sidecar summary
5. The tool writes:
   - experiment markdown summary
   - optional structured summary sidecar
   - optional selected-driver timeline diagnostics

## Optimization Follow-Up

After diff and diagnostics exist, D009/D010 optimization should proceed in small increments:

1. Generate a current diagnostic timeline for D009 and D010.
2. Identify the first high-confidence penalty source from logs and evaluator behavior.
3. Add or adjust a generic parser/planner/scorer rule driven by parsed preferences.
4. Add focused unit tests for the behavior.
5. Run local unit tests and full smoke simulation.
6. Generate a new experiment report with baseline delta.

Candidate optimization areas are:

- Required cargo planning when the cargo is not immediately selectable.
- Sequence-task planning for pickup, home, visit, or stay requirements.
- Earlier no-drive and rest-window reservation.
- Better tradeoff between monthly deadhead limits and income.

Each production behavior change must be expressible without checking driver IDs.

## Model Usage

`qwen3.5-flash` is the only allowed model. The model call path should remain narrow:

- Use it only for fallback parsing of unknown strong preference text.
- Record token usage in experiment summaries.
- Avoid high-frequency calls during normal cargo selection.
- Fail closed or fall back to wait when an unknown strong preference cannot be parsed safely.

The model is not expected to improve the current score directly unless future hidden or newly surfaced preference text is not covered by deterministic parsing.

## Testing

Add or update tests for:

- Parsing a previous experiment summary or structured sidecar.
- Computing total and per-driver deltas.
- Formatting positive, negative, and zero deltas.
- Handling missing baseline drivers.
- Producing selected-driver timeline diagnostics from minimal action logs.

Existing unit tests for parser, guard, planner, scorer, decision service, and report generation must continue to pass.

## Acceptance Criteria

1. A new report can compare current results to a previous experiment.
2. The report includes a clear `Delta` section.
3. D009/D010 timeline diagnostics can be generated without production driver-ID hardcoding.
4. Unit tests cover the new report and diagnostic behavior.
5. The next full simulation report records enough information to decide whether D009/D010 changes improved score or regressed other drivers.
